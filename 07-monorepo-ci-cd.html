Monorepo, CI et CD de la data platform

Fin août 2026, j'ai fusionné le dépôt de l'application et celui de la data platform. La CI vérifie ce qu'on ne peut pas vérifier en relisant : du SQL qui compile sur Athena, des stacks dans le bon ordre, des failles connues. La CD ne redéploie que ce qui a changé depuis le dernier déploiement réussi, en dev et en prod, à chaque merge.

Pourquoi un monorepo

Les deux dépôts ne partageaient aucun code, mais ils étaient couplés de deux façons : une API dans les deux sens (chaque service appelle l'autre) et une base PostgreSQL commune. Ce que je cherchais :

  • une seule PR pour un changement qui touche les deux côtés ;
  • des contrats d'API et des schémas de base qui ne dérivent plus ;
  • une CI qui détecte la dérive ;
  • aucun déploiement pour un commit qui ne touche pas le périmètre.

Hors périmètre, volontairement : le code partagé, la génération de code, les packages communs. Chaque périmètre garde sa stack et son outillage : TypeScript et yarn pour l'app, Python 3.12, uv et un Makefile pour la data.

Un commit atomique n'est pas un déploiement atomique. L'app part sur Scalingo, la data platform sur AWS, dans un ordre que je ne contrôle pas. Le schéma partagé évolue donc toujours en expand/contract : ajouter une colonne nullable et déployer les deux côtés, backfiller, basculer la lecture, puis supprimer l'ancienne colonne dans une release suivante. Le monorepo supprime la dérive, pas le séquencement.

Les règles qui tiennent l'ensemble

  • L'app est la source de vérité pour tout ce qui est partagé : elle possède le DDL des tables communes et la définition des routes. La data platform lit et écrit, mais ne fait pas évoluer ces schémas.
  • Un périmètre par commit, sauf quand le changement touche un contrat partagé.
  • Les propriétaires de code : la racine et .github/ appartiennent aux deux équipes, app/ à l'équipe app. data-platform/ est volontairement sans propriétaire, pour que le périmètre data reste autonome.

La fusion, techniquement

  • Le dépôt de l'app a servi d'hôte et a gardé ses SHA : ses fichiers ont été déplacés dans app/ avec git mv.
  • L'historique de la data platform a été réécrit avec git filter-repo --to-subdirectory-filter data-platform, puis fusionné avec --allow-unrelated-histories.
  • Conséquence : git log -- data-platform/… remonte des années sans option, alors que git log -- app/… s'arrête au déplacement et demande --follow.
  • J'ai fait la bascule une première fois en POC, puis rejouée pour de vrai une semaine plus tard. Entre les deux, les dépôts avaient bougé de 117 et 282 commits. Le rejeu a trouvé deux pièges : un git diff lancé depuis la racine sortait des chemins en data-platform/src/…, qui ne correspondaient plus à aucune règle de sélection des stacks (le déploiement intelligent n'aurait rien déployé, il a fallu --relative) ; et le .gitignore racine avait perdu quatre règles ancrées.

La CI d'une PR

Un seul workflow, déclenché sur toutes les PR, sans filtre de chemins : un check requis qui ne démarre jamais reste en attente pour toujours. Un premier job regarde si la PR touche la data platform. Si non, les étapes sont sautées mais le job conclut en succès : un check requis « skipped » n'est pas un check qui passe. Un nouveau push annule le run en cours, car deux builds dbt se battraient pour le même namespace.

dbt Validate : prouver que le SQL compile, sans données

Chaque PR construit le projet dbt dans des bases jetables wavo_dp_ci_pr<N>_*, supprimées en fin de job. Construire sur de vraies données n'a jamais été envisageable : les quatre plus grosses tables parentes pèsent 2,9 milliards de lignes en prod.

  • Des sources vides typées comme la prod. Environ 19 fixtures réelles, copiées de la prod, pour les tests qui en ont besoin. Toutes les autres sources sont des tables vides, avec les types de colonnes de la prod. Le build prouve que le SQL est valide sur Athena (colonnes, types, fonctions) sans déplacer de données. Il ne prouve pas que le SQL est juste : chaque modèle renvoie zéro ligne.
  • Des sources propres à la PR. Quand une PR modifie la déclaration d'une table bronze, cette table est recréée avec ses nouveaux types dans le namespace de la PR. Une alternative a été écartée : élargir les fixtures partagées. Une PR non mergée y laisserait son champ, deux PR se battraient sur la mise à jour Glue (qui remplace tout le schéma), et Iceberg ignore de toute façon les modifications de schéma faites dans Glue.
  • Slim CI : --select state:modified+ --defer --favor-state contre le manifest d'un namespace ci_main, plus l'aval des sources modifiées. Un changement de dbt_project.yml, des macros, des tests ou des seeds déclenche un build complet.
  • Après le build :
    • chaque nouveau modèle doit déclarer son contrat ;
    • le fichier Python des routes de merge, généré depuis le DAG, doit être identique à sa version commitée (git diff --exit-code) ;
    • en mode complet, une sonde vérifie que le nettoyage des orphelins garde une table bronze et signale une vue inconnue ;
    • un test refuse qu'un modèle lise une couche supérieure (landing < bronze < silver < gold).
  • Les réglages : 12 à 16 threads, et un intervalle de polling Athena de 0,25 s. Comme chaque modèle est une vue ou un CTAS vide, le build n'est que de la latence aller-retour vers Athena : 342 des 480 requêtes finissent en moins d'une seconde.
Pourquoi un namespace ci_maindbt Validate ne tournait que sur les PR. Main pouvait donc casser en silence, et c'est la PR suivante, qui n'y était pour rien, qui passait au rouge. Par ailleurs, le Slim CI qui diffait contre la prod sélectionnait trop de modèles (avec @, 489 nœuds au lieu de 95 après la modification d'un modèle central) et n'allait pas plus vite que le build complet : 270 s contre 259. Un workflow sur main reconstruit maintenant ci_main et publie son manifest ; les PR diffent contre lui. Contrepartie : pendant les cinq minutes de reconstruction, une PR peut échouer sur une table absente, et il suffit de la relancer.

La CD : ne déployer que ce qui a bougé

Chaque merge sur main déclenche la CD, en dev et en prod en parallèle, sans intervention. Il n'y a pas de validation humaine avant la prod : sur un dépôt privé avec le plan Team de GitHub, les reviewers obligatoires d'environnement ne sont pas disponibles. La PR est le point de contrôle.

Le diff depuis le dernier déploiement réussi

  • Le SHA du dernier déploiement réussi est stocké dans un paramètre SSM, par environnement. La CD diffe SHA enregistré..HEAD, pas seulement le dernier commit. Un merge qui ne touchait que l'app, et qui a donc sauté la CD, est rattrapé au merge suivant.
  • Le SHA n'avance que si tout a réussi, et jamais en arrière. Un seul script l'écrit.
  • Les runs sont sérialisés, sans annulation : deux runs simultanés se disputeraient le SHA et le manifest dbt.
  • Un garde-fou compare le commit à appliquer au dernier appliqué, via l'API GitHub. Un run relancé qui arrive après un commit plus récent n'applique rien. C'est arrivé : la deuxième tentative d'un vieux run avait supprimé des tables qu'un commit plus récent venait de déclarer.

Les vagues. Avant, un déploiement complet prenait 21,5 minutes, une stack à la fois, alors que j'avais déjà vu neuf déploiements tourner en parallèle sans problème. Le script qui vérifie l'ordre des stacks (à partir des paramètres SSM produits et consommés, et des ARN construits) calcule maintenant des niveaux de dépendance : 29 stacks en 6 vagues, neuf en parallèle au maximum. Le code qui refuserait un mauvais regroupement est celui qui le produit.

dbt dans la CD

  • Ordre imposé : stacks, puis catalogue, puis dbt. Le premier merge qui ajoutait à la fois une table bronze et la vue qui la lit est passé au rouge, parce que dbt avait tourné avant la création de la table. J'ai préféré sérialiser plutôt que tolérer l'absence : une vue sautée est une vue qui reste, en silence, sur ses anciennes colonnes.
  • Sélection : <chemins migrés>,state:modified+ contre le manifest de l'environnement stocké sur S3, en excluant les tables écrites par le pipeline.
  • Un mode plan par défaut : sans le flag d'application de l'environnement, la CD compile et liste les orphelins à supprimer, sans rien appliquer. C'est ce qui ressemble le plus à un change set CloudFormation, que dbt ne propose pas.
  • Deux manifests publiés : l'état pour le prochain state:modified, et un manifest de lignage complet que le pipeline d'ingestion lit avant de supprimer une colonne de landing.
  • Même sur un déploiement vide, un contrôle vérifie que chaque table déclarée existe toujours dans Glue (une table supprimée hors CloudFormation), et reconstruit les vues figées sur un ancien schéma.

Les landings promues au merge

Pendant son développement, une branche peut faire évoluer le schéma d'une table landing dans son environnement éphémère. Au merge, la CD exporte ces schémas et les promeut en dev et en prod. Le schéma le plus récent gagne, d'après des estampilles posées sur la table (date, hash, origine). Le UpdateTime de Glue est inutilisable pour ça, car une copie le remet à zéro.

Les environnements éphémères

Chaque branche se déploie sur un environnement devN loué dans un pool, et la CD le libère au merge. Le fonctionnement du pool, et son pendant côté app avec les branches Neon et les review apps, font l'objet du module 9.

Les pièges

Ce que la CD ne déploie pasUn changement des seuls paramètres d'environnement ne redéploie que deux stacks. Un changement de modèle Bedrock a ainsi été mergé avec une CD verte, sans que la stack qui le portait soit redéployée : la prod est restée sur l'ancien modèle jusqu'à un déploiement manuel. Les modèles gold ne sont pas non plus dans la sélection dbt de la CD. Un vert ne signifie donc pas « tout est en prod » : je vérifie l'objet déployé.
Un diff cumulatifUn ajout suivi de son revert entre deux CD s'annulent. Et une stack restée en échec (UPDATE_ROLLBACK_COMPLETE) n'est pas retentée : une CD verte n'atteste pas qu'une stack rouge a été reprise.
Le diff local inclut le working treeC'est voulu, pour ne pas oublier un template modifié non commité. Mais un « essai à blanc » lancé en local déploie bel et bien ce qui n'est pas commité.
SAM et le cache d'uploadSAM a sauté un upload (« File with same data already exists ») et redéployé un ancien package : une Lambda de prod a gardé l'ancien code alors que sa voisine, dans la même stack, avait reçu le nouveau. Je vérifie le code déployé, pas le log de déploiement.
Une layer mise à jour, des Lambdas oubliéesLe script qui rattachait la nouvelle version de layer listait les fonctions sans pagination : 50 fonctions sur 203, seules 15 sur 63 ont été rattachées.
Le worker dbt embarque le projetMettre un modèle en prod à la main ne suffit pas : sans redéployer le worker, la nuit suivante, il réapplique l'ancien SQL de son image.
Le bypass adminLes admins peuvent pousser directement sur main, et ce push part en prod sans qu'aucun test ait tourné. C'est encore ouvert chez Wavo.

À reprendre chez vous

  1. Un check requis sans filtre de chemins, qui conclut en succès quand il n'a rien à faire.
  2. dbt Validate sur des sources vides typées comme la prod : on obtient la preuve que le SQL compile, sans payer les données.
  3. Un namespace ci_main reconstruit à chaque merge, contre lequel diffent les PR.
  4. Un SHA du dernier déploiement réussi par environnement, qui n'avance que sur un succès complet.
  5. Des vagues de déploiement calculées depuis le graphe de dépendances, par le même code qui le vérifie.
  6. dbt après l'infra, jamais en parallèle.
