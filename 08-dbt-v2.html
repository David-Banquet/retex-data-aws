dbt v2 et le connecteur Athena

dbt Core 2.0 est sorti le 14 septembre 2026 : une réécriture complète en Rust, sous licence Apache 2.0. Athena n'en fait pas encore partie. Le connecteur est en cours d'écriture par la communauté, et j'y contribue. Ce module fait le point en octobre 2026 : ce que v2 apporte, où en est Athena, et comment s'y préparer.

Ce qu'est dbt v2

C'est le moteur qui s'appelait « dbt Fusion », devenu la branche principale de dbt-labs/dbt et relicencié en Apache 2.0. La v1 en Python continue sur la branche 1.latest : elle ne disparaît pas du jour au lendemain. Chronologie : alpha le 1er juin 2026, 2.0.0 le 14 septembre, 2.0.5 quatre jours plus tard.

ApportCe que ça change chez Wavo
Parse et compile beaucoup plus rapidesLe cycle édition → compilation devient quasi instantané, et la CI paie moins chaque parse.
Plus strict : une spécification du langage vérifiée dès le parseDes erreurs qui n'apparaissaient qu'à l'exécution sur Athena sortent avant. En contrepartie, un projet v1 tolérant peut refuser de parser.
Un binaire autonome, sans runtime PythonChez Wavo, dbt est isolé derrière un wrapper uvx pour que ses quarante dépendances n'atteignent jamais mes Lambdas. Avec v2, ce problème n'existe plus, et l'image du worker ECS s'allège.
Artefacts en ParquetLe manifest.json reste produit : mon pipeline, qui lit le lignage, n'est pas cassé.
Ce qui n'est pas dans le moteur ouvertLa compréhension avancée du SQL, le linting et le lignage par colonne restent des fonctionnalités « Fusion » sous licence produit, activées par dbt login. Le code Apache 2.0 n'en contient que les clients. Et sur Athena, l'analyse statique est de toute façon désactivée pour l'instant : dbt debug l'indique.

Pour tester la compatibilité de votre projet sans rien migrer : dbt-core 1.12 propose dbt parse --use-v2-parser. C'est la première chose à lancer.

Le connecteur Athena, où on en est

Rien n'est encore mergé. Le code avance, mais tout attend la revue de dbt Labs. Aucune date de sortie n'est annoncée publiquement.

Le suivi se fait sur l'issue dbt-labs/dbt#16252. Le travail est découpé en une série de PR, écrites par deux contributeurs externes à dbt Labs, avec quelques correctifs de ma part :

Le driver Go, dans dbt-labs/athena, a lui aussi trois PR ouvertes : #15 (timestamps), #19 (Glue, S3, STS) et #20 (statistiques de requêtes).

Ce qui fonctionne déjà, sur la branche d'exécution

  • Tables Iceberg : merge, append, microbatch, partitionnement par day().
  • Tables Hive : insert_overwrite avec réécriture partielle de partitions, et le mode ha.
  • Snapshots, seeds, persist_docs.
  • Tags Lake Formation et data cell filters, workgroup imposé, assume role. C'est le point qui vous concerne le plus.
  • Le catalogue Glue déclaré dans catalogs.yml.

Ce qui coince encore

  • insert_overwrite sur une partition de type timestamp : le driver se trompe d'unité. Le correctif est dans athena#15, pas encore mergé.
  • Les partitions bucket() ne sont pas supportées.
  • S3 Tables n'a pas été testé.
  • Pour rappel, même en 1.11, insert_overwrite est réservé à Hive. Iceberg n'accepte que append, merge et microbatch.

Premières mesures

Sur un petit projet de test (11 modèles, eu-west-1), comparé à dbt-core 1.11 avec dbt-athena 1.11. Chiffres publiés sur #16252 :

1,8 s → 0,6 sparse du projet
42 → 0requêtes information_schema pendant un run : les métadonnées passent par l'API Glue
24 / 24tests verts, avec le correctif des seeds (#16460)

Le temps total d'un run ne bouge presque pas à 11 modèles : sur Athena, c'est l'exécution des requêtes qui domine, pas dbt. Le gain se verra sur les gros projets, au parse et à la compilation, donc surtout en CI et en développement.

Mes contributions

Je ne réécris pas le connecteur. J'éprouve les branches sur des cas réels et je corrige ce qui casse :

  • dbt v2 : la casse des column_types dans les seeds (#16460, qui corrige #16459) ; les types dans les contrats de modèles (#16571) ; la vérification des schémas requis, qui listait toutes les bases du catalogue (#16698, ouverte le 12 octobre).
  • Directement dans les branches de la série : le quoting du data catalog, et les types complexes dans le DDL.
  • dbt-athena 1.x, dans dbt-adapters : catalogue avec un schéma manquant (#2195), types complexes dans le DDL (#2211), entrées de catalogue inconnues (#2212).

Toutes ces PR attendent encore une revue.

Comment s'y préparer

  1. Restez sur dbt-core 1.x et dbt-athena 1.11 en production. Ils restent maintenus, et rien ne presse.
  2. Lancez dbt parse --use-v2-parser avec dbt-core 1.12 : vous verrez ce que la sévérité de v2 refusera dans votre projet, sans rien changer.
  3. Si vous utilisez Lake Formation, testez vos tags et vos filtres sur la branche d'exécution dès qu'elle est mergée. C'est un des rares points où Athena diffère vraiment des autres adaptateurs.
  4. Ne comptez pas sur le lignage par colonne dans le moteur ouvert : il relève de l'offre sous licence.
  5. Suivez #16252. Un retour d'usage, surtout sur Lake Formation ou sur un gros catalogue Glue, est utile aux contributeurs. Les approbations de mainteneur sont le goulot.
