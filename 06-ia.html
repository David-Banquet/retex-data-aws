Module 6 · Data et IA

L'IA dans la chaîne de données

Ce que les LLM font concrètement chez Wavo : catégoriser, extraire, aller chercher la donnée là où il n'y a pas d'API, répondre aux équipes métier, et travailler sur la plateforme elle-même. À chaque fois, la sortie du modèle entre dans le lakehouse comme n'importe quelle autre source : landing, puis bronze historisé.

Catégoriser des transactions bancaires

Une cascade en trois étapes, mergées dans cet ordre : mots-clés (un seed dbt), puis un modèle Claude sur Bedrock pour ce que les mots-clés n'ont pas couvert, puis les corrections manuelles. L'ordre fait la précédence : une proposition du modèle n'écrase jamais une correction humaine.

  • L'unité de travail est le libellé distinct, pas la transaction. Environ 350 000 lignes non catégorisées portaient 108 000 couples (libellé, signe). Un appel répond pour toutes les transactions qui partagent un libellé.
  • Les propositions sont stockées et servent de cache : un libellé déjà vu ne coûte aucun appel. En régime de croisière, un run représente trois lots et une minute.
  • Un budget par organisation (nombre de libellés par run), et --no-cache réservé au lendemain d'un changement de prompt.
  • Un seul chemin de code : le script de backfill appelle les mêmes Lambdas que la Step Function. Il n'existe pas de version « outil » qui diverge de la prod.
Quand la regex tombe, la facture monteMa table de mots-clés s'est vidée (un seed écrit dans un bucket qui expire en un jour, module 5). Plus aucun mot-clé ne matchait, et toutes les nouvelles transactions partaient chez le modèle. Rien n'a cassé, c'est le coût qui a révélé le problème. Surveillez le taux de couverture de chaque étage de la cascade.

Détail Bedrock : certains modèles récents refusent un toolChoice forcé. Je suis passé en auto, avec une consigne explicite dans le prompt et une validation de la sortie.

Des agents navigateur pour les ERP sans API

Beaucoup de mes sources sont des ERP sans API exploitable. Un agent pilote un navigateur dans une tâche ECS : il se connecte, exporte le rapport et le dépose en landing. Le reste du pipeline ne voit pas la différence avec une autre source.

  • Filtrer uniquement sur les dates à l'export, et appliquer les filtres métier dans le silver. La plateforme garde ainsi une trace exhaustive de ce qui a été collecté.
  • Une garde sur les connexions : plusieurs runs en parallèle sur le même compte client ont déjà provoqué six logins simultanés. Le pipeline vérifie l'URL, l'identifiant et le mot de passe avant chaque tentative.
  • Le jour où l'éditeur change son export, les colonnes landing changent. Les nouvelles sont ajoutées automatiquement, mais une ancienne n'est retirée que si le lignage dbt prouve que plus aucun modèle ne la lit.
  • Le cache de prompt : sur les longues sessions, j'élague les captures d'écran par blocs plutôt qu'une par une, pour ne pas invalider le cache à chaque étape.

Le lignage dbt devient ici une donnée de production. Le manifest.json publié par la CD est lu par le pipeline d'ingestion pour savoir quelles colonnes sont encore utilisées. Pensez-y si vous publiez déjà vos manifests : c'est un graphe de dépendances gratuit et toujours à jour.

Extraire des documents

Relevés bancaires, factures, liasses fiscales : des Lambdas d'extraction par LLM produisent des lignes typées (modèles Pydantic) qui entrent en landing puis en bronze, avec la même historisation que le reste. Les documents longs sont découpés en morceaux, et il faut ensuite recoller ce qui a été coupé : une facture répartie sur deux morceaux doit garder toutes ses lignes.

Un MCP data pour les équipes métier

Les commerciaux et les ops interrogent la donnée depuis Claude, via un serveur MCP maison. Trois choix de conception ont fait la différence :

  • Un outil get_context à appeler avant tout SQL : le périmètre, les tables, les conventions (montants en centimes, fuseau de Paris, fraîcheur des données).
  • Des outils dédiés pour les indicateurs canoniques (encours, frais facturés, revenu récurrent, bilan) : le modèle ne réinvente jamais une formule. Le SQL libre reste possible pour le reste, en lecture seule et plafonné.
  • Un outil report_data_feedback : quand une question n'a pas pu être bien répondue, le modèle demande à l'utilisateur comment il a fini par trouver, et le remonte. C'est mon backlog de qualité de données, alimenté par l'usage.
Une réponse fausse est pire qu'une absence de réponseLa réplique lue par le MCP gardait des tables supprimées en prod : pg_restore --clean ne supprime que ce que le dump contient. Le modèle répondait avec des chiffres figés au jour de la suppression, sans la moindre erreur. Recréez la réplique de zéro, ou comparez régulièrement la liste de ses tables à celle de la source.

Claude Code sur la plateforme

La plus grande part du travail décrit dans ce dossier (migration dbt, bascule DuckDB, scripts de parité) a été faite avec Claude Code. Ce qui le rend utile sur une plateforme data :

  • Un CLAUDE.md par zone du code (lambdas, stacks, dbt, tests), qui ne contient que ce qui a déjà mordu et ne se voit pas dans le code.
  • Des skills pour déployer, lancer un workflow, faire un smoke test sur un environnement éphémère, surveiller, diagnostiquer.
  • Un accès Athena par MCP, et un wrapper de lecture prod qui ne peut pas écrire. Les écritures prod sont refusées par un hook et remises à un humain avec la commande exacte.
  • Des alertes qui lancent une session : quand un job casse la nuit, l'alerte Slack ouvre une session Claude isolée sur une MicroVM. Elle diagnostique avec un accès prod en lecture seule, ouvre la tâche et propose une PR draft ; un humain relit et merge.

Le détail de ce dernier point fait l'objet d'une page à part, « Les boucles de la Software Factory ». Je peux vous l'envoyer.
