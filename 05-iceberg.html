Guidelines Iceberg sur Athena et Glue

Iceberg pour tout ce qui reçoit des updates ou des deletes, Parquet Hive pour le reste. Ces règles viennent toutes d'un incident ou d'une mesure. Les plus importantes concernent moins Iceberg lui-même que ce qui l'entoure : S3, Glue, Step Functions.

Quand utiliser Iceberg

CoucheFormatPourquoi
LandingFichiers brutsTrace de ce qui a été reçu, rejouable
BronzeParquet Hive, partitionné par ingestion_datetimeAppend-only : Iceberg n'apporte rien, et l'historize reste un simple dépôt de fichiers
SilverIcebergMERGE, corrections, suppressions
GoldIceberg pour les tables, vues sinonRafraîchissement par périmètre (DELETE puis INSERT)

Création d'une table

  • Partitionnez selon le prédicat de vos écritures, pas selon celui de vos lectures. Chez Wavo, c'est organization_id : chaque merge et chaque refresh se fait client par client, et ne réécrit donc que les fichiers d'une partition.
  • Propriétés que je pose sur toutes les tables : 
    'optimize_rewrite_delete_file_threshold': '2',
'optimize_rewrite_data_file_threshold':   '2',
'write_target_data_file_size_bytes':      '536870912'   -- 512 Mo
    Le seuil de fichiers de données passe de 5 (défaut Athena) à 2, pour qu'OPTIMIZE compacte aussi les partitions peu écrites, qui sont la majorité quand on partitionne par client.
  • Lisez les propriétés avec SHOW CREATE TABLE, pas dans Glue. Pour une table Iceberg, Glue ne contient que metadata_location et table_type : un contrôle basé sur Glue signale toutes les propriétés comme absentes, à tort.
  • Méfiez-vous des tables recréées à la main : deux de mes tables avaient perdu leurs propriétés d'optimisation et gagné une compression différente lors d'une recréation passée. Personne ne s'en souvenait.

Maintenance

Une Step Function quotidienne, déclenchée la nuit en heure de Paris, parcourt toutes les tables Iceberg :

  • Les tables de refresh portent en plus VACUUM et OPTIMIZE en post-hook dbt : chaque run crée un snapshot, et elles sont réécrites plusieurs fois par jour.
  • OPTIMIZE qui échoue sur des fichiers manquants (« Missing required files to delete ») : je tente un VACUUM, puis je relance une fois. Si l'échec persiste, il faut le remonter, pas l'avaler.
  • La sauvegarde se fait par CTAS dans une base dédiée, sous le nom <table>_<AAAAMMJJ>, conservée 14 jours. Surtout pas « DDL depuis le fichier SQL, puis INSERT … SELECT * » : un ADD COLUMNS ajoute la colonne à la fin, alors que le fichier la place où elle se lit le mieux, et l'INSERT associe par position.
  • Je ne sauvegarde que les tables qui accumulent : celles qu'on peut recalculer à partir des sources n'en ont pas besoin. Ce choix doit être explicite (une liste, une propriété de table) et non déduit d'une convention de fichiers. La nôtre reposait sur la présence d'un fichier SQL, et a failli basculer le jour où j'ai supprimé du SQL mort.

La sonde de lisibilité

C'est le dernier état de la maintenance : un COUNT(*) sur chaque table Iceberg. Athena le sert depuis les manifests, pour 0 octet scanné. Mesuré en prod : 57 tables en 15 secondes. Une table qui refuse le COUNT après le VACUUM et l'OPTIMIZE est cassée, pas en cours d'écriture. L'exécution échoue et nomme les tables concernées.

Pourquoi pas un contrôle de fraîcheur ? Certaines tables gold ne sont rafraîchies qu'à la demande et restent légitimement intactes pendant des semaines. Un seuil assez serré pour détecter la panne alerterait à chaque quinzaine calme. L'illisibilité, c'est la panne elle-même. Et le signal existait déjà : le VACUUM échouait chaque nuit sur trois tables mortes, mais l'erreur était rangée dans un warning pendant que l'exécution se terminait en SUCCEEDED.

S3 sous les tables

Jamais de lifecycle d'expiration sur un bucket de tablesUne règle à 14 jours, posée un an plus tôt sur le bucket gold, supprimait data et metadata de toute table Iceberg non réécrite depuis deux semaines, alors que Glue pointait toujours dessus (ICEBERG_MISSING_METADATA). Le premier diagnostic parlait de snapshot corrompu. C'était l'infra, et la panne revenait tous les 14 jours sur les tables peu écrites. La croissance se borne avec VACUUM et OPTIMIZE, pas avec S3.
Même piège, autre bucketLe staging dir d'Athena expire en un jour, ce qui est normal pour des résultats de requêtes. Mais tout ce qui y atterrit par défaut (un seed dbt sans s3_data_dir, par exemple) devient une table que Glue croit pleine et qui se lit vide. Vérifiez la Location de chaque table.

Pour réparer une table dont les fichiers ont disparu : DROP, puis reconstruction depuis les sources ou depuis la dernière sauvegarde CTAS. Pour une table calculée, un refresh suffit.

Évolutions de schéma

  • Ajouter une colonne : on_schema_change='append_new_columns' s'en charge. Ne passez jamais à sync_all_columns sur Iceberg, qui supprime les colonnes du live absentes du modèle.
  • Changer un type : ajout d'une nouvelle colonne, backfill, suppression de l'ancienne, renommage, avec COUNT et SUM vérifiés à chaque étape, puis un OPTIMIZE. Le tout dans un script daté, versionné, idempotent. Et avant le déploiement du code : Athena arrondit sans prévenir un DECIMAL mergé dans une colonne int.
  • Renommer une colonne : dbt ne sait pas le faire. Script DDL, puis reconstruction à la main des vues qui la lisent.
  • Après un DROP COLUMN, Glue garde la colonne comme non courante. Un script qui lit le schéma depuis Glue doit filtrer ces colonnes.
  • Une vue Glue stocke ses propres types de colonnes. Après un changement de type en dessous, elle est périmée. Si CREATE OR REPLACE bute sur l'ancienne définition, il faut un DROP puis une recréation.

Écritures concurrentes

  • Deux commits simultanés sur la même table : l'un échoue (ICEBERG_COMMIT_ERROR), sans corruption. Je réessaie, et je borne la contention avec des permis par table (module 4).
  • Une exécution de Step Functions ne doit pas rattraper cette erreur dans un Catch : un Catch coûte le redrive. Une erreur rattrapée termine l'exécution en SUCCEEDED, et le redrive ne rejoue que les FAILED. Je laisse échouer, sauf raison écrite dans le template.
  • Plusieurs runs qui reconstruisent la même vue en même temps donnent un ConcurrentModificationException côté Glue. Décalez les relances.

En résumé

  1. Iceberg pour silver et gold, Parquet Hive pour le bronze en append-only.
  2. Partitionner selon le prédicat d'écriture.
  3. Seuils d'OPTIMIZE à 2, fichiers cibles de 512 Mo.
  4. VACUUM et OPTIMIZE chaque nuit, et après chaque refresh.
  5. Sauvegarde CTAS des tables qui accumulent, et elles seules.
  6. Aucune expiration S3 sous une table.
  7. Un COUNT(*) quotidien sur chaque table, qui fait échouer l'exécution.
  8. Les évolutions de type dans un script daté, avant le code.
