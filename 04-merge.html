Module 4 · Leviers d'optimisation

Merge dans Iceberg

Le passage bronze → silver : plusieurs sources (un ERP par client, des exports mail, des API) fusionnent dans une même table Iceberg par MERGE. C'est là que se logent les bugs les plus coûteux, parce qu'un merge raté ne lève aucune erreur : il insère des doublons ou écrase en silence.

Deux formes de cibles

Cible de mergeCible de refresh
NatureAccumule l'historique, ligne par ligneFonction déterministe de ses sources
Matérialisation dbtincremental, stratégie merge, unique_keyincremental, stratégie append, avec un DELETE du périmètre en pre-hook
Reconstruction complèteJamais : on perdrait l'historiquePossible, sur tout ou partie du périmètre
ExempleStocks, ventes, flux d'inventaire par fournisseurAgrégats et indicateurs gold

La config d'une cible de merge

Onze modèles ne diffèrent que par leur famille et leur config. Le corps est donc partagé dans une macro, et chaque modèle ne déclare que ce qui lui est propre :

config(
    materialized='incremental',
    incremental_strategy='merge',
    unique_key=unique_key,
    merge_exclude_columns=['created_at'],        # jamais réécrit après l'insert
    merge_update_columns_rules=rules,            # coalesce par colonne optionnelle
    on_schema_change='append_new_columns',       # jamais sync_all_columns sur Iceberg
    unique_tmp_table_suffix=true,                # staging unique : runs concurrents possibles
    table_type='iceberg',
    table_properties={
        'optimize_rewrite_delete_file_threshold': '2',
        'optimize_rewrite_data_file_threshold': '2',
        'write_target_data_file_size_bytes': '536870912',
    },
    incremental_predicates=(
        ["target.organization_id = '" ~ var('organization_id') ~ "'"]
        if var('organization_id', none) else none
    ),
)

Pourquoi coalesce sur les colonnes optionnelles

L'ancienne Lambda construisait son UPDATE SET à partir de l'intersection colonnes source ∩ cible, source par source : une colonne qu'un fournisseur ne fournit pas restait intacte dans la cible. Une union dbt doit émettre toutes les colonnes pour tous les membres, et le UPDATE SET de dbt écrirait alors le NULL d'alignement par-dessus une valeur existante. La règle coalesce rétablit le comportement : la source gagne quand elle a une valeur, la cible survit sinon. La seule chose qu'elle ne reproduit pas, c'est un membre qui voudrait volontairement remettre une valeur à NULL. Sur des snapshots d'ERP, ça n'arrive jamais.

Levier 1 : le fan-out par organisation

Un pipeline par client merge seulement les lignes de ce client. Il y a deux moitiés, et elles vont ensemble :

  • un WHERE organization_id = … dans le modèle, qui restreint la table de staging ;
  • un incremental_predicates sur la cible, qui restreint le ON du MERGE.
Une moitié sans l'autre produit des doublonsSans le prédicat sur la cible, le ON ne porte que sur la clé et compare à toute la table ; Iceberg doit alors lire toute la table. Et avec le prédicat appliqué à un run multi-organisations (fan-in), la staging contient tous les clients mais la cible n'en expose qu'un : tous les autres sont réinsérés. Les deux moitiés dépendent de la même variable, et doivent le rester.

Le partitionnement des cibles par organization_id rend ce prédicat rentable : le MERGE ne réécrit que les fichiers d'une partition.

Levier 2 : borner la concurrence par table écrite

Iceberg gère la concurrence de façon optimiste : deux MERGE simultanés sur la même table, l'un des deux échoue au commit (ICEBERG_COMMIT_ERROR). Les données ne sont pas corrompues, mais il faut réessayer, et sous forte contention les retries s'enchaînent.

  • Un compteur de permis par table écrite, dans DynamoDB avec écritures conditionnelles, pris avant le MERGE et rendu après. « ventes ≤ 3 » et « stocks ≤ 3 » sont deux compteurs distincts : six merges tournent en parallèle sans qu'aucune table n'en voie plus de trois.
  • Un compteur partagé, pas un sémaphore en mémoire : ce dernier ne borne plus rien dès que le service tourne sur plus d'une tâche ECS.
  • C'est un contrôle de contention, pas de correction. La correction vient des tables de staging uniques et des retries Iceberg. Si on traite le compteur comme un invariant, on finit par le mettre à 1 « par sécurité » et on sérialise un pipeline qui n'en avait pas besoin.
  • Trois réglages indépendants : MaxConcurrency des Step Functions (combien de pipelines), le nombre de process dbt par tâche, et --threads (parallélisme dans un DAG). Montez d'abord le nombre de tâches ECS, en vous guidant sur le temps passé en file : dbt attend surtout Athena, et plusieurs petits workers limitent l'impact d'un crash.
  • Un verrou par analyse quand plusieurs étapes doivent voir des tables stables : le verrou couvre toute l'exécution, ce que des permis par étape ne savent pas exprimer.

En pratique, espacez aussi les relances manuelles : trois redrives lancés coup sur coup donnent trois publications concurrentes qui se rejettent.

Levier 3 : ne réécrire que ce qui a changé

Un hash par ligne, calculé dans la vue source, sert de condition de mise à jour : une ligne matchée dont le hash n'a pas bougé n'est pas réécrite, donc aucun fichier de suppression ni nouveau fichier de données n'est produit.

{% macro record_hash(fields) -%}
    MD5(TO_UTF8(
        {%- for field in fields %}
        COALESCE(CAST("{{ field }}" AS VARCHAR), ''){% if not loop.last %} || '|' ||{% endif %}
        {%- endfor %}
    )) AS record_hash
{%- endmacro %}
  • L'ordre des champs fait partie du contrat. Le modifier change tous les hash, et le merge suivant réécrit toutes les lignes qu'il matche. La liste est donc passée explicitement, modèle par modèle.
  • Mettez le hash dans la vue de base, pas dans une vue au-dessus. J'avais 23 vues SELECT *, MD5(…) : Athena stocke l'expansion du *, et dès que l'ordre des colonnes de la vue de base a changé, elles sont devenues illisibles (VIEW_IS_STALE), sans que rien ne le signale.

Levier 4 : des familles de sources sans liste à maintenir

Plusieurs sources (un fournisseur ERP chacune) alimentent une même cible. L'appartenance à une famille est un tag dbt, et l'union est générée à partir du tag. Une assertion fait échouer le build si le tag et la liste déclarée divergent. Ajouter un fournisseur revient à écrire un modèle et à le taguer.

Deux exceptions où l'union est fausse :

  • Quand l'ordre fait la précédence. Mes étapes de catégorisation (mots-clés, LLM, manuel) sont mergées l'une après l'autre : la correction manuelle gagne parce qu'elle passe en dernier. Une union ferait perdre cet ordre.
  • Quand deux membres produisent volontairement la même clé (une ligne rattrapée depuis une source et recalculée depuis une autre) : une union donnerait deux lignes au MERGE pour une seule clé.

Dans ces deux cas, je garde un membre par run.

Les clés : là où naissent les doublons

Une colonne NULL dans la cléEn SQL, NULL = NULL n'est jamais vrai : le MERGE ne matche jamais et réinsère à chaque run. J'avais 1 814 lignes pour 25 clés distinctes. Les trois remèdes (une valeur sentinelle, retirer la colonne de la clé, supprimer les doublons) modifient tous des données stockées : c'est une décision métier, pas un correctif technique.
Une clé trop courteSans le fournisseur dans la clé, une organisation présente sur trois marketplaces ne gardait que la dernière mergée.
Un SELECT DISTINCT de précautionL'ancienne Lambda dédoublonnait la source avant le merge. Mesuré : toutes les sources étaient déjà uniques sur leur clé. Ce DISTINCT ne protégeait de rien et coûtait un tri.

Une requête à lancer chez vous : pour chaque table cible, COUNT(*) comparé à COUNT(DISTINCT clé), et le nombre de lignes dont une colonne de la clé est NULL. Après la bascule, c'est le critère que j'ai retenu : des insertions seulement, aucune clé dupliquée, aucune colonne de clé NULL.

Les cibles de refresh

config(
    materialized='incremental',
    incremental_strategy='append',
    pre_hook='{{ delete_refresh_scope() }}',   -- DELETE du périmètre, ou de toute la table
    post_hook=['VACUUM {{ this }}',
               'OPTIMIZE {{ this }} REWRITE DATA USING BIN_PACK'],
    table_type='iceberg',
)
  • Le même modèle couvre le rafraîchissement complet et le partiel : il suffit de passer ou non un filtre (--vars), comme le faisait l'ancienne Lambda avec son payload.
  • VACUUM puis OPTIMIZE en post-hook, parce que chaque run ajoute un snapshot et que rien d'autre ne les élague. Désactivés dans les namespaces de CI, où la table vient d'être créée vide : environ 3 s gagnées par modèle.
  • Une garde sur les modèles coûteux : certains ne doivent jamais être reconstruits entièrement. Sans filtre, ils liraient toutes les organisations et videraient la table d'abord. Le modèle refuse alors de tourner. La Lambda n'en avait pas besoin, personne n'envoyait de payload sans filtre ; avec dbt, le run est une ligne de commande, et la garde tient en quatre lignes.

Les backfills

  • Athena plafonne une requête DML à 30 minutes. Une table de 82 millions de lignes se backfille une organisation à la fois.
  • Un script de migration doit être idempotent face aux colonnes que Glue garde après une suppression Iceberg (non courantes) : sinon, une relance voit la colonne supprimée et refait toute la migration.
