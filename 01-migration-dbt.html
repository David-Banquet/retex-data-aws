Module 1 · Retour d'expérience

Migrer vers dbt sans jamais avoir deux propriétaires

Évaluation en juillet 2026, bascule complète en dev et en prod le 25 août, sans interruption de service. Toutes les vues et tables silver et gold appartiennent désormais à dbt. Ce module raconte comment, et ce que je referais autrement.

Le point de départ : j'avais réinventé dbt à la main

  • 237 templates SQL avec substitution ${ENV} faite en Python.
  • Un ordre de déploiement tenu dans la doc : « les tables bronze avant les vues », « tel stack avant tel autre ».
  • Environ 6 000 lignes de CloudFormation sur 13 stacks, juste pour déclarer des vues et des tables via une custom resource.
  • Un registre Python (clés primaires, champs obligatoires, cible Iceberg) lu par une Lambda merge_dataset, plus une Lambda refresh_table (DELETE puis INSERT).
  • Des vues de contrôle (doublons, valeurs manquantes, bornes) lues par une Lambda après coup.
  • Deux pipelines qui portaient chacun leur propre copie du graphe de dépendances gold → silver, avec un parcours en profondeur écrit à la main.

Le gain principal de dbt, c'est le DAG calculé à partir de ref(). Toute une classe de problèmes (ordre de déploiement, dépendances croisées entre stacks) disparaît. La doc et le lignage viennent en bonus.

Ce que dbt remplace, et ce qu'il ne remplace pas

Reste en placePasse dans dbt

dbt Core suffit, pas besoin de dbt Cloud. J'ai regardé SQLMesh : il a un moteur Athena et son plan remplace mieux les change sets CloudFormation. J'ai choisi dbt pour la maturité de l'adaptateur Athena, l'écosystème et le recrutement.

Les règles qui ont rendu la migration sûre

  1. Un seul propriétaire par objet Glue, à tout instant. dbt et CloudFormation ne gèrent jamais le même objet. Le passage de relais se fait en deux déploiements : d'abord DeletionPolicy: Retain seul, vérifié sur le template déployé (pas dans git), puis le retrait de la ressource. CloudFormation affiche DELETE_SKIPPED, l'objet reste intact, dbt le reprend. Avec une custom resource, Retain signifie concrètement que CloudFormation n'envoie jamais l'événement Delete à la Lambda qui gère l'objet.
  2. Jamais de renommage d'identifiant logique dans un template : CloudFormation supprime alors l'objet par son nom physique.
  3. La parité est le critère, pas la relecture. dbt construit dans un namespace « shadow » qui lit les sources de prod, et un test compare au live : nombre de lignes et checksum sur toutes les colonnes. Une phase n'avance pas sur « le SQL a l'air équivalent ».
  4. Les vues avant les tables. Une vue se reprend avec CREATE OR REPLACE et se rend en quelques minutes. Une table, c'est de la donnée qui bouge.
  5. Les deux systèmes restent déployables pendant une release après chaque bascule. Les anciennes Lambdas sont restées en place jusqu'à 48 h consécutives de zéro invocation, lues dans CloudWatch, dans les deux environnements.
  6. Une phase doit pouvoir s'arrêter sans état mixte : chaque objet a encore un seul propriétaire, l'ancienne Lambda est toujours déployée, et le nettoyage automatique n'est pas encore activé sur la base. Si l'une des trois conditions manque, je découpe la phase.

La bascule se fait dans la Lambda, pas dans les pipelines

Les appels aux Lambdas de merge et de refresh étaient éparpillés dans les state machines : 19 points d'appel. Les modifier un par un aurait produit un gros diff, difficile à annuler vite. J'ai donc mis un flag par dataset dans le registre, qui part déjà avec la Lambda :

  • Nom d'exécution déterministe (dataset + id de run) : si la Lambda est relancée, elle reçoit ExecutionAlreadyExists et se rattache au run en cours. On obtient ainsi un retry sûr sans verrou.
  • Les backfills ne passent pas par là : la Lambda bloque pendant le poll, et elle est plafonnée à 15 minutes.
  • Une fois tout basculé, j'ai câblé les pipelines directement sur dbt : ils envoient +<cible> et dbt renvoie les tables et leur ordre. Comparé aux deux graphes faits main sur les 14 cibles : 13 identiques, et le 14e était une erreur de la carte manuelle.

Le nettoyage des orphelins

dbt ne supprime jamais un objet dont on a retiré le modèle, contrairement à CloudFormation. Une macro drop_orphans compare le manifest au catalogue et supprime ce que dbt ne connaît plus. Elle n'est active que sur une liste explicite de bases, par environnement, et seulement quand une base ne contient plus rien qui appartienne à CloudFormation. Elle échoue fermée : une base absente de la liste est ignorée. Le premier run réel en prod a supprimé 23 vues mortes, et rien d'autre.

À savoir avant de l'activer : à partir de là, un merge qui supprime ou renomme un modèle supprime l'objet correspondant en prod. C'est le cycle de vie voulu, et c'est aussi la première fois qu'un merge peut écrire dans le catalogue Glue de prod.

Les pièges dbt-athena

Une table adoptée ignore la config du modèlepartitioned_by et table_properties ne s'appliquent qu'à la création. Sur une table existante, dbt merge dedans tel quel et répond OK. Le jour où quelqu'un lance --full-refresh, la table est recréée avec la config du modèle (chez Wavo, je perdais la compression ZSTD). Alignez le live sur le modèle avant de l'adopter, par un script DDL daté. Attention : pour une table Iceberg, Glue ne montre pas les propriétés, il faut SHOW CREATE TABLE.
on_schema_change : append_new_columns, jamais sync_all_columnsSur Iceberg, sync_all_columns supprime les colonnes du live absentes du modèle. Six des tables de la plateforme avaient des colonnes ajoutées par un ALTER jamais reporté dans le DDL.
Un seed sans s3_data_dir s'évaporeIl atterrit dans le staging dir d'Athena. Si ce bucket expire ses objets au bout d'un jour, la table reste dans Glue mais se lit vide le lendemain. Et la CD, qui sélectionne par chemin models/, ne reseedait jamais les seeds.
Un bucket codé en dur dans +s3_data_dirLe dbt_project.yml pointait sur le bucket de dev : un merge de prod aurait créé sa table de staging en dev. Le bucket dépend maintenant de l'environnement, dans une expression, pas dans une variable qu'on peut oublier de passer.
Les tags sont additifs dans l'arbreUn +tags au niveau du projet tague tous les modèles : mon --select tag:sales renvoyait 45 modèles au lieu de 7.
state:modified+ s'intersecte sélecteur par sélecteur--select "a b,state:modified+" n'intersecte que le dernier terme et reconstruit tout a à chaque run.
Pas de --target, mauvaise cibleLe worker ECS tournait sur la cible par défaut du profiles.yml, celle de la CI. Et les paramètres de prod n'écrasaient pas les valeurs dbt de dev : un déploiement prod aurait construit sur les bases de dev.
Un run local compile le working treeLancé depuis un checkout en retard de 200 commits, un dbt build --target prod a recréé 84 vues avec du vieux SQL, sans erreur. Pour un run manuel, partez d'un worktree sur origin/main.
Athena stocke l'expansion du SELECT *Une vue SELECT *, MD5(…) au-dessus d'une autre devient VIEW_IS_STALE dès que l'ordre des colonnes de la vue de base change. Un count(*) ne le révèle pas : vérifiez les types dans information_schema.columns.
Pas de modèles Python sur AthenaCe qui était généré en Python devient une macro Jinja. Python génère des fichiers une fois (migration), Jinja génère du SQL à chaque run.

La parité, en pratique

  • Elle est ponctuelle, donc je rafraîchis les fixtures juste avant de mesurer. Un modèle a échoué de 21 lignes le lendemain d'un succès, simplement parce que le bronze avait été rechargé entre-temps. Un échec sur des fixtures périmées est une fixture périmée jusqu'à preuve du contraire.
  • Pas de test de parité dans la CI des PR : les fixtures sont un snapshot, la prod bouge, et un test qui passe au rouge pour une raison étrangère au diff apprend à ignorer le rouge. La parité se lance délibérément, après un rafraîchissement.
  • Les colonnes non déterministes s'excluent une par une, mesurées. approx_percentile, les sommes de doubles (écart jusqu'à 1,8e-15), un ROW_NUMBER() sans départage sur des dates identiques. Je n'exclus jamais un modèle entier.
  • Méfiez-vous d'un test qui passe trop facilement. Une variable mal placée redirigeait aussi le sujet du test : 19 sur 21 passaient parce que le test comparait le live à lui-même.
  • Pour une table incrémentale, la parité shadow ne suffit pas : une table construite de zéro ne contient pas l'historique accumulé. Le bon critère est l'effet comparé : j'imprime l'instruction exacte qu'aurait exécutée l'ancienne Lambda, et je compare les deux résultats sur les mêmes sources.
  • Chaque zéro est vérifié. Une vue vide après bascule est exactement le symptôme d'une bascule ratée. Sur 22 vues vides, toutes avaient une explication (fixtures de dev, delta à l'équilibre, filtre légitime). Aucune n'a été acceptée sans vérification.
