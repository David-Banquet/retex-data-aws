Module 3 · Leviers d'optimisation

Historize landing → bronze

L'étape la plus fréquente de la plateforme : chaque fichier reçu devient une partition bronze en Parquet. Mes partitions sont souvent petites, et c'est ce qui change tout : le coût fixe d'Athena y dépasse largement celui de la copie.

Le modèle

  • Landing : le fichier brut (JSON, JSONL, CSV, Excel converti en CSV), une partition par réception.
  • Bronze _hist : Parquet, partitionné par ingestion_datetime, et par organization_id quand la source est par client. Rien n'est jamais écrasé : les partitions s'empilent.
  • Bronze _latest : une vue par table, générée par une macro dbt, qui ne garde que la dernière partition. Il n'existe que deux formes : la dernière partition globale, ou la dernière par organisation.
{% macro latest_from_hist(hist_relation, partition_keys=[]) %}
  {% if partition_keys %}
  SELECT * FROM {{ hist_relation }}
  WHERE ({{ partition_keys | join(', ') }}, ingestion_datetime) IN (
      SELECT {{ partition_keys | join(', ') }}, MAX(ingestion_datetime)
      FROM {{ hist_relation }} GROUP BY {{ partition_keys | join(', ') }})
  {% else %}
  SELECT * FROM {{ hist_relation }}
  WHERE ingestion_datetime = (SELECT MAX(ingestion_datetime) FROM {{ hist_relation }})
  {% endif %}
{% endmacro %}

Les clés sont déclarées par modèle, pas déduites du catalogue au moment de la requête. Avant, une évolution de schéma pouvait changer en silence les lignes renvoyées par une vue _latest. Maintenant, la clé est visible dans le code et relue en PR.

Le chemin d'une partition

Levier 1 : arrêter MSCK REPAIR

MSCK REPAIR rescanne tous les préfixes de la table pour découvrir ce qui est nouveau : 43 s en médiane sur les tables landing de la plateforme, 117 s en queue de distribution. Or le pipeline qui vient d'écrire une partition sait laquelle. Un glue:CreatePartition ciblé, c'est un appel d'API.

C'est le levier le moins cher de ce dossier : quelques lignes de code, aucun nouveau moteur. Commencez par là.

Un point d'attention : enregistrez la partition que l'étape a effectivement écrite, pas celle déduite d'un filtre, et faites-le avant de rendre la main. Une partition présente sur S3 mais inconnue de Glue est invisible pour Athena, sans aucune erreur.

Levier 2 : DuckDB dans une Lambda

Avec Athena, historiser coûte environ 20 s fixes : MSCK REPAIR, puis un INSERT INTO dont la planification et le commit dépassent la copie elle-même. DuckDB lit le fichier landing et écrit le Parquet bronze dans le même process.

PartitionAthenaDuckDB
14 Mo20,7 s1,6 s
1,4 Go29,5 s20,5 s

Plus la partition grossit, plus l'écart se réduit. Le bon critère : mesurez la part du coût fixe sur vos partitions réelles. Si elle domine, DuckDB est un gain net. Sur de très gros volumes, gardez Athena ou Glue.

La méthode de bascule

  1. Un sélecteur de moteur : une variable d'environnement fixe le défaut, un événement peut le surcharger. Le retour arrière ne demande aucun déploiement.
  2. Les deux moteurs en parallèle, d'abord en dev et sur les environnements éphémères, puis en prod. La prod est passée en dernier : le risque plausible y était un dépassement mémoire sur une partition de 10 Go, pas une lenteur.
  3. Une comparaison partition par partition entre les deux moteurs (et même entre deux comptes AWS), avant de couper l'ancien chemin.
  4. Un aiguillage par format : chaque partition landing part vers le moteur qui la lit comme Athena la lirait. Le CSV est passé sur DuckDB dans un second temps.

Réglages Lambda

  • Mémoire : le RSS mesuré dépasse nettement le budget de DuckDB (buffers JSON, runtime Python, allocateur). Je donne à DuckDB 50 % de la mémoire de la fonction. Une partition de 2,6 Go a culminé à 5,1 Go sur une Lambda de 8 Go.
  • Threads : Lambda donne un vCPU par 1 769 Mo. Dans la même région, la latence S3 est assez faible pour que le travail soit limité par le CPU. Doubler le nombre de threads par vCPU a apporté 11 % ; la vraie limite, ce sont les 125 Mo de budget dont DuckDB a besoin par thread.
  • Extensions : elles sont livrées dans une layer dédiée, mais seulement en secours. Le téléchargement depuis le dépôt DuckDB est plus rapide que la lecture de la layer (0,57 s contre 7,3 s). Exception : httpfs, qui ne peut pas se télécharger lui-même.
  • Layer séparée : une dépendance par consommateur, pour que les Lambdas qui n'utilisent pas DuckDB ne paient pas son poids au démarrage.
  • Gros objets JSON : relevez maximum_object_size (64 Mo chez Wavo) et loguez l'URI S3 complète de l'enregistrement fautif. Sinon, une seule ligne trop grosse fait échouer toute la partition sans dire où.

Ce que le SerDe Hive faisait en silence

Le vrai travail de la bascule, c'est de reproduire la tolérance de l'ancien chemin. Chaque point ci-dessous produisait soit des NULL silencieux, soit un rejet :

La casse des colonnesLe crawler avait mis les colonnes en minuscules, alors que la source écrit en camelCase. Le JSON SerDe compare sans tenir compte de la casse, DuckDB non : sans aliasing explicite, toutes les colonnes camelCase arrivent NULL.
L'association par positionUn INSERT INTO sans liste de colonnes associe par position, pas par nom. Mes sources mail ont des en-têtes accentués et espacés, face à des noms bronze en ASCII.
Un scalaire dans un tableauUn champ array<T> qui contient un scalaire nu : le SerDe le lit comme une liste d'un élément, DuckDB rejette la partition entière. Seules les colonnes qui portent des tableaux sont lues en JSON puis reconstruites ; le reste reste typé, pour ne parser qu'une fois des documents de 230 Ko.
Du JSON derrière une étiquette Parquet13 des 113 tables bronze de la plateforme étaient du JSON texte déclaré classification: parquet. Y écrire du vrai Parquet produit un fichier qu'Athena ne sait plus ouvrir, avec une erreur qui ne donne pas la cause. Le format d'écriture se lit dans le SerDe de la table, pas dans sa classification.
La partition videL'INSERT Athena lit zéro ligne et réussit. Le nouveau chemin levait une erreur.
Les horodatagesLes tables landing déclarent leurs instants en string. Un instant rendu différemment arrive tel quel en bronze, sans que rien ne passe au rouge. La sortie doit rester identique octet pour octet à l'ancienne. Quant à l'estampille de partition bronze, elle est restée en UTC parce que tout l'historique l'était.
Un champ de struct déclaré d'avanceQuand le bronze déclare un champ que la landing n'a pas encore, il faut le remplir de NULL plutôt que d'échouer.

L'incident du lancement : le nouveau chemin rendait la main avant d'enregistrer la partition dans Glue. Résultat : 48 partitions présentes sur S3, inconnues de Glue. Je les ai retrouvées en comparant S3 au bronze (plutôt qu'en partant de la liste de ce que quelqu'un avait remarqué), puis rejouées depuis les fichiers landing. Le rejeu est idempotent grâce à l'estampille, et il respecte l'ordre que lit _latest.

Levier 3 : ne plus inférer les schémas

Un crawler qui invente des noms de champsUn seul passage manuel a inféré un struct dont les membres s'appelaient comme des dates. Le parser de types d'Athena les refuse, et toute vue au-dessus échoue. La réparation doit toucher la table, mais aussi chaque partition, qui garde sa propre copie des types (HIVE_PARTITION_SCHEMA_MISMATCH, 729 partitions en dev). Les vues, qui stockent elles aussi les types, doivent être supprimées puis recréées : un CREATE OR REPLACE bute sur l'ancienne définition.
  • Schémas déclarés, plus aucun crawler planifié.
  • Élargir un type (int → decimal) : landing et bronze changent ensemble dans Glue. Les partitions existantes gardent leur schéma int, qu'Athena convertit à la lecture. Côté Iceberg : ajout, backfill, suppression, renommage, avec COUNT et SUM vérifiés avant et après. Et toujours avant le déploiement du code : Athena arrondit sans prévenir un DECIMAL mergé dans une colonne int.
  • Quand une source change de colonnes (un ERP qui change d'export) : les nouvelles colonnes sont ajoutées automatiquement, mais une ancienne n'est retirée de la landing que si le lignage dbt prouve que plus aucun modèle ne la lit. Il faut alors un premier run (même rouge) pour ajouter les colonnes, puis relancer la CD pour republier le lignage.
